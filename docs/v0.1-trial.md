# Lessons from the v0.1 trial

The first public release already incorporated several changes from using the tree in Obsidian. This record brings those changes together with the refinements documented in v0.1.1.

## Give each ticket one outcome

- a. Use concise title case. “Desk Mat Fit” is enough when the criteria say how to check the fit. Familiar abbreviations can keep diagram labels short. Put the full name in the ticket when it helps readers find or understand it.
- b. Treat “and” between outcomes as a prompt to split the ticket. A parent can summarize three venue options. If each quote can be requested, checked, or accepted independently, give each quote a child ticket.
- c. Put work under the outcome it advances and use related links for other relevant branches. If a parent broadens, keep completed work as a child when it still contributes.
- d. Keep the constraints that affect several children on the parent. Put case-specific details on the child that owns them. A short sketch or map can help when the reader needs to understand how places or steps fit together.

## Make agent work reviewable

- a. Create or identify the ticket when starting substantial work. Record the approach, sources or checks, and what remains open before linking the result. State the cases, time ranges, or versions you actually checked so a later reader can judge the coverage.
- b. Give research its own ticket when it supports a separate decision. “Desk Mat Comparison” can reach Done when the comparison is complete. “Desk Mat Choice” stays open until the user has made the choice.
- c. Put each required check in acceptance criteria. When a remaining check serves a different outcome, put it on the relevant ticket and link it. Preparing a file, seeing it in a companion app, and using it successfully on the target device can each require separate evidence.

## Keep Notes usable on the next pass

- a. When the user asks for a refresh, reread current Notes from disk and reconcile recent edits before acting. Leave unresolved notes in place. When Notes is empty, keep `1.` followed by one ASCII space so the user can type their next entry.
- b. Write Change Log entries that make sense after the original Notes are cleared. Include the substance of the feedback and what changed. Link affected tickets or notes when useful. For example, “The fit check needs clear depth in front of the monitor. Added a measurement criterion to the fit ticket.”

## Make the tree easy to scan

- a. Give distinct checks, options, and supplies separate list lines. Use stable letter labels for unordered items and numbers for steps that must happen in sequence.
- b. Keep detailed results in focused vault notes and link to the relevant note or heading. When splitting a note with existing inbound links, preserve the old headings as an index that points to the new locations, or repair the referring links.
- c. Keep working material in the vault when possible. Outside links can point to evidence or an action on another service. A short reminder can link to the relevant vault note for details. If an attachment is missing on another device, check selective sync.
- d. Put each node's ticket title on its own line. On the next line, use a monospace ID followed by a status dot and written status. Use the double-sided box for a ticket that opens a continuation. Verify that the arrows still advance to the right on narrow displays.

## Rename with synced edits in mind

1. Read the latest ticket, including Notes and the Change Log, after sync. Keep the ID and pilot one rename or move before a batch.
2. Verify links in both directions. Check the parent and child properties, related links, and links in note bodies. Regenerate the diagrams and their Markdown links, validate the tree, and follow a link to the renamed ticket.
3. If sync recreates the old file with the same ID, compare the copies before removing either one. Preserve newer human edits in the surviving ticket.

## Questions from the trial

- a. Try making the current ticket's root label plain in its own continuation, with a compact link back to its parent beside it.
- b. Research can span several local decisions. Try keeping shared research under its owning outcome and linking it from the local decisions that need it.
